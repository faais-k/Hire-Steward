# ADR-0012: Job Discovery Source-Access Model and Lever Evaluation Candidate

- **Status:** Proposed (Approved by product owner as product direction; source remains `NEEDS_REVIEW` and disabled pending formal activation gate)
- **Date:** 2026-10-28

## Context and Scope

Hire-steward is a local-first, personal job discovery and application-preparation assistant operating solely on behalf of an individual candidate. The product architecture is built on deterministic policy enforcement, verifiable evidence boundaries, and candidate control.

Hire-steward is **not** an unconstrained web scraper, centralized job board aggregator, or multi-tenant crawling platform. It operates under a strictly scoped source-access model:
1. **User-specified employer boards only:** Hire-steward monitors only employer job boards explicitly designated and configured by the candidate (e.g., specific company handles or board tokens). It does not crawl the open web, harvest arbitrary directory listings, or discover unconfigured employer boards.
2. **Local execution and persistence:** The discovery agent runs locally on the candidate's personal computer, persisting discovered listings, deduplication markers, and match assessments in local PostgreSQL storage.
3. **Candidate-facing discovery:** Ingested listings are filtered deterministically against candidate-configured preferences (e.g., hard compensation floor per ADR-0006/ADR-0007).

To transition from synthetic fixtures to real job discovery, Hire-steward requires an initial applicant tracking system (ATS) candidate source for read-only listing evaluation.

## Decision

The product owner has approved the following product direction:

1. **Lever as first candidate for evaluation:** Lever's public Postings API (v0) is designated as the first candidate for additional read-only source-feasibility evaluation.
2. **Read-only job discovery:** Access is strictly confined to querying published job postings and their associated descriptions via documented public GET endpoints.
3. **Manual application handoff (`MANUAL_ONLY`):** Application submission is strictly manual. Hire-steward presents the canonical posting URL (`hostedUrl` or `applyUrl`) directly to the candidate in their personal browser. Automated application submission via ATS APIs or browser automation is out of scope.
4. **No global crawling or evasion:** Hire-steward will not implement global crawlers, uncredentialed mass scraping, credential harvesting, proxy rotation, CAPTCHA bypass, or rate-limit evasion mechanisms.
5. **No live access or activation yet:** This decision establishes product direction and an architectural evaluation model. It is **not** blanket legal authorization, final approval of Lever for live access, or authorization to activate an operational adapter. The source capability state remains strictly `NEEDS_REVIEW` and disabled.

## Evidence from Official Documentation

Official Lever Postings API documentation was reviewed on 2026-10-28:
- **Primary documentation repository:** [Lever Postings API (GitHub)](https://github.com/lever/postings-api)
- **Documented listing endpoint:** `GET https://api.lever.co/v0/postings/{company}` (EU: `https://api.eu.lever.co/v0/postings/{company}`)
- **Documented detail endpoint:** `GET https://api.lever.co/v0/postings/{company}/{posting_id}`
- **Documented application endpoint:** `POST /v0/postings/{company}/{posting_id}?key=APIKEY`

Key documented properties:
- **Third-party scraping acknowledgement:** The official documentation explicitly states:
  > *"all job postings in the published state are publicly viewable. These jobs may be scraped by third parties. All other jobs are completely hidden from the jobs API."*
- **Authentication:** Public listing and detail GET endpoints require no API key, bearer token, or HTTP authentication. Application creation (`POST`) explicitly requires an API key generated by a Super Admin for that company account (`?key=APIKEY`), reinforcing that candidate tools cannot submit applications through the public API without employer-issued integration credentials.
- **Identifiers and content:** Postings have stable alphanumeric string identifiers (`id`), publication timestamps in millisecond epoch (`createdAt`), structured descriptions in HTML (`description`), plain text (`descriptionPlain`), structured bullet lists (`lists`), closing text (`additional`), and canonical navigation URLs (`hostedUrl`, `applyUrl`).
- **Pagination:** The listing endpoint supports integer pagination via `skip` (offset) and `limit` query parameters.

## Limitations and Terms/Policy Distinction

Hire-steward explicitly distinguishes four categories of technical, policy, and contractual authority:
1. **API documentation and technical capability:** The documentation confirms that published postings can technically be queried via unauthenticated HTTP GET requests and that Lever contemplates third-party scraping.
2. **Customer terms of service:** Lever's published Terms of Service (https://www.lever.co/legal/terms-of-service) describes its scope in terms of customers acquiring and using Lever software and services. The reviewed sources do not conclusively establish how those terms, or any other applicable terms, govern Hire-steward's proposed unauthenticated public-API usage. The applicability question remains unresolved and requires source-specific clarification or appropriate legal review.
3. **Policy applicable to unauthenticated public API access:** The official Postings API repository notes that published postings are publicly viewable and may be scraped by third parties. However, whether a separate unauthenticated website terms of use imposes restrictions on programmatic access is `NOT ESTABLISHED BY REVIEWED SOURCES`. Lever's repository statement cannot be converted into blanket legal indemnity or a bilateral contract.
4. **Unresolved multi-employer recurring aggregation:** Whether an automated personal agent polling multiple user-specified employer boards on a recurring schedule is deemed permitted under applicable laws and terms is `NOT ESTABLISHED BY REVIEWED SOURCES` and remains contractually unconfirmed.

**Explicit unknowns:**
- Numeric rate limits and burst thresholds for the public v0 Postings API are `NOT ESTABLISHED BY REVIEWED SOURCES`. (The 10 req/s steady / 20 req/s burst limit documented for Lever's v1 Data API applies strictly to authenticated developer endpoints and cannot be assumed for the public v0 endpoint).
- Real-world CDN/WAF throttling, IP-level rate limiting, and blocking thresholds remain unverified.

## Safety Controls and Anti-Evasion Policy

To ensure ethical, non-disruptive, and conservative network interactions, any future Lever read-only adapter must enforce the following safety controls:

1. **Conservative polling schedule:**
   - Polling is restricted to candidate-configured employer boards only.
   - Frequency is strictly bounded: at most once every 12 to 24 hours per configured employer board.
   - Continuous polling loops and high-frequency checks are prohibited.
2. **Bounded network timeouts:**
   - TCP connection timeout: maximum 5 seconds.
   - Request read timeout: maximum 15 seconds.
3. **HTTP caching and conditional requests:**
   - Honor standard HTTP caching headers (`ETag`, `If-None-Match`, `Last-Modified`, `If-Modified-Since`) where supported to prevent unnecessary payload transfers.
4. **Bounded retries with backoff:**
   - Maximum 2 retries on transient network failures or 5xx server errors.
   - Retries must use exponential backoff with randomized jitter.
5. **Fail-closed rate-limit and error handling:**
   - On HTTP `429 Too Many Requests`: Immediately stop polling, parse and respect `Retry-After` if present (or enforce a default multi-hour cooldown), and log an operational warning.
   - On HTTP `403 Forbidden` or `401 Unauthorized`: Treat as an access failure; immediately disable polling for that employer board and surface a notification to the candidate.
6. **Circuit breaker:**
   - Three consecutive network or HTTP failures for an employer board trips the circuit breaker for that board.
   - A tripped circuit breaker suspends polling for that board and requires manual candidate inspection or reset.
7. **Strict anti-evasion policy:**
   - **Transparent identity:** Requests must include an honest, identifiable `User-Agent` header disclosing Hire-steward and repository/support contact information.
   - **No IP proxy rotation:** Using commercial proxy networks, residential proxies, or IP rotating pools is strictly prohibited.
   - **No CAPTCHA bypass:** Automated CAPTCHA solving, headless browser obfuscation, or header fingerprint spoofing is strictly prohibited.
   - **No ban evasion:** If an IP address or board token is blocked, the system must fail closed and report the condition. Bypassing access controls is forbidden.

## Data Minimization and Proposed Retention Policy

Hire-steward collects and stores only data required for job matching, criteria filtering, and application preparation:

1. **Retained fields:**
   - Source metadata: Source name (`lever`), employer handle (`company`), and posting ID (`id`).
   - Posting data: Job title (`text`), publication timestamp (`createdAt`), category/location metadata (`categories.location`, `commitment`, `team`).
   - Content: Job description text (`descriptionPlain`, `description`, `lists`, `additional`) for deterministic keyword and compensation evaluation.
   - Links: Canonical job page (`hostedUrl`) and manual apply URL (`applyUrl`).
2. **Excluded fields:**
   - Tracking scripts, marketing pixels, social share URLs, and extraneous employer internal identifiers are discarded upon ingestion.
3. **Proposed retention policy:**
   - **Active postings:** Retained locally while returned by the employer board in subsequent discovery runs.
   - **Closed/Removed postings:** Postings that cease to appear on the employer board are transitioned to status `REMOVED` or `CLOSED` rather than being immediately deleted, preserving the integrity of existing candidate notes, match evaluations, and application drafts.
   - **Pruning unreferenced postings:** Postings marked `REMOVED` that have no candidate association (no bookmark, notes, fact-matching review, or draft application) are automatically purged after 60 days.
   - **Raw payloads:** Raw HTTP response bodies are discarded after parsing, or optionally stored in content-addressed blob storage subject to candidate document storage quotas.

## Activation Gate

The Lever source adapter capability state remains **`NEEDS_REVIEW`** and **disabled**.

The existing Phase 0 roadmap exit gate in `docs/phases.md` requires: *"No unresolved license or source-permission blocker for the first source."*

Owner acceptance of the proposed product direction or residual risk does **not** itself establish source permission or resolve this roadmap exit gate. Neither unauthenticated public endpoint availability nor Lever's third-party scraping documentation note constitutes affirmative legal permission or a formal license.

Phase 0 remains strictly **`IN_PROGRESS / NOT PASSED`**. The roadmap exit gate is not modified.

Before Lever can be transitioned from `NEEDS_REVIEW` to `VERIFIED_READ_ONLY` and before any live source requests or background polling can occur, the owner must either:
1. **Obtain adequate source-specific clarification or appropriate legal review** confirming that Hire-steward's proposed read-only polling of user-specified boards complies with applicable terms and legal requirements; OR
2. **Separately review and formally decide whether the product's acceptance criteria should change** regarding third-party source permissions and risk posture.

Additionally, before live read-only activation, the following technical prerequisites must be satisfied:
- Owner approval of a single-request live test protocol executed against an agreed employer board to inspect live response headers, caching, and schema conformity without bulk polling;
- Verified offline unit/integration test suite passing with static recorded fixtures, demonstrating timeout handling, circuit breaking, bounded retries, and honest `User-Agent` identification.

## Implementation Boundary

Upon owner review of this ADR:
- **Permitted:**
  - Designing source adapter interfaces and models using offline recorded/synthetic JSON fixtures.
  - Implementing unit tests validating pagination parsing, circuit breaking, and retry logic against mock servers.
  - Documenting employer board configuration schemas.
- **Prohibited:**
  - Making live HTTP requests to Lever or any ATS production endpoints.
  - Implementing automated background polling, cron schedules, or persistent daemons.
  - Enabling any source adapter in runtime configurations or database migrations.

## Consequences and Alternatives

### Alternative 1 (Selected): Proceed with Lever as First Candidate for Evaluation
- *Advantages:* Lever's official documentation explicitly acknowledges that published postings are publicly viewable and may be scraped by third parties. The API provides clear offset pagination (`skip`, `limit`) and plain text descriptions alongside HTML.
- *Disadvantages:* Public rate limits and WAF thresholds are unstated. The legal status of recurring multi-employer aggregation remains contractually unconfirmed.
- *Conclusion:* Best-documented first candidate for technical and source-permission evaluation, based on Lever's explicit documentation about published postings and third-party scraping.

### Alternative 2: Investigate Greenhouse Job Board API First
- *Advantages:* Highly common ATS; clean integer job IDs; `?content=true` parameter returns complete descriptions.
- *Disadvantages:* Documentation does not mention third-party scraping; intended use is framed around custom employer career pages; no offset or cursor pagination parameters are documented.
- *Conclusion:* Retained in `NEEDS_REVIEW` as a potential secondary candidate after Lever.

### Alternative 3: Investigate Ashby Public API First
- *Advantages:* Public Job Posting API requires no key; explicit support for structured compensation (`?includeCompensation=true`).
- *Disadvantages:* Documentation explicitly states it is designed for a single organization's custom job board; cross-employer aggregation is unaddressed; unauthenticated rate limits are unstated.
- *Conclusion:* Retained in `NEEDS_REVIEW` as a candidate for structured compensation evaluation once single-board access models are mature.

### Alternative 4: Pause All ATS Integrations; Rely on Manual Entry or Open Data
- *Advantages:* Zero legal or terms risk regarding ATS platforms.
- *Disadvantages:* Defeats Hire-steward's core product mission of automating candidate job search and discovery.
- *Conclusion:* Rejected. Proceeding with Lever under a strictly bounded, user-configured read-only evaluation model provides a transparent, cautious path forward for evaluation.
